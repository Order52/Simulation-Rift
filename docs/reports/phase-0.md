## Findings that changed the design

1. **age recipient encryption is not sender-authenticated (X1).** Anyone who knows the vault's public recipient can produce a well-formed index file. The index is now HMAC-authenticated with a key derived from the vault identity, and the MAC is verified before parsing (architecture §14.1). A test forges an index using only the public recipient and confirms it is rejected.
2. **`tough` normalizes hostile target names instead of rejecting them (X2).** `../../etc/passwd` becomes `etc/passwd`, and `/etc/passwd` stays absolute, so `dir.join(name.resolved())` can escape the staging directory. Rift stages only allowlisted flat names that are already in normal form (architecture §13.2).
3. **Three idempotence bugs in URL canonicalization (X3)**, all found by property tests: port detection before trailing-dot removal, Punycode moving a literal `%` next to hex digits, and repeated empty-port stripping. All are fixed and kept as regression cases. Without idempotence, the same URL could hash differently depending on how many times it had been normalized.

4. **The latest YARA-X (1.21.0) pins Wasmtime 45.0.3, which carries seven 2026 RustSec advisories** (found by `cargo deny`). Triage against Rift's configuration: one `Engine`, synchronous calls only, core runtime only (no component model, async, or `wasmtime-wasi`), and guest wasm generated by YARA-X itself from signed rules.
   - Six advisories cannot apply: they need two engines, `wasmtime-wasi`, the component model or async.
   - One (recursive-type stack overflow) could crash the worker. That is contained by confinement and reported as "not fully scanned".

   The exceptions are scoped and justified in `deny.toml`. **Action:** remove them when a YARA-X release depends on Wasmtime ≥ 48.0.6, which fixes all seven. `bincode` (used by YARA-X for serialization) is unmaintained but not vulnerable. Rift never deserializes untrusted bincode.

5. **YARA-X timeouts start a thread, which the Linux worker must never do (L2).** `Scanner::set_timeout` lazily spawns a global heartbeat thread. Under lockdown the `clone` is denied and the worker dies; the controller reported this as a failure, not a clean scan. Starting the thread before lockdown would have been a real hole: seccomp without TSYNC and Landlock confine only the calling thread. The design changes (architecture §7.3):
   - the Linux supervisor enforces scan deadlines by killing the worker (`rift_worker::Deadline::Supervisor`), with `RLIMIT_CPU` as backstop;
   - Android keeps YARA-X's timeout, since the app cannot kill its isolated process;
   - `lockdown::apply` refuses to run unless exactly one thread exists;
   - `crates/rift-worker/tests/no_threads.rs` fails if a scan or image decode ever starts a thread. It passes on Ubuntu x86_64 in CI (run 39058785140).
6. **WebKitGTK's network process is not sandboxed, and the web-process check has to be precise (L1).**
   - In a native package the network process has no seccomp filter and no new namespaces, though it parses HTTP, TLS and cookies for every site. That supports shipping Flatpak first (architecture §9.2).
   - The first probe matched the `bwrap` launcher by command line and reported it as an unconfined web process. The check now uses `comm`, and runs for every new web process, since WebKit starts new ones as sites change.

7. **WebView writes browsing state outside the per-generation directory (A2).** On API 36, WebView 133 writes `shared_prefs/AwOriginVisitLoggerPrefs.xml`, a set of hashes of visited origins with a date, at the app level, where `setDataDirectorySuffix` does not reach. Deleting only the suffixed directories would have left a record of where the user browsed. Reset now deletes all of `shared_prefs/`, Rift must never use SharedPreferences, and the post-reset check compares the inventory with an allowlist of Rift's own files (architecture §15).
8. **Some downloads never reach Rift (A3).** `blob:` and `data:` downloads do not call `DownloadListener` at all, so Rift cannot even show "cannot be captured". POST responses do reach it, but cannot be re-fetched (HTTP 405). The product claim is limited to downloads served at a URL (architecture §8.5).
9. **`isolated_app` still allows `AF_UNIX` sockets and executable memory (A6), and NoNewPrivs is 0 in the worker.** No network or file access was possible, so A6 passes, but the worker is less confined than the Linux one. A per-thread seccomp filter is the Phase 2 candidate, with its limits stated (architecture §8.6).
10. **The native library adds 14 MB (arm64) to 18 MB (x86_64) per ABI to the APK (A5)**, against a 25 MB budget. It is stored uncompressed, so any further native code on Android, such as `tough` and `aws-lc-rs` for X2, must fit in the remaining ~11 MB (arm64). Cargo output was 23 MB before stripping; release builds now strip symbols, as the Android Gradle plugin already does when packaging.
11. **A worker from the system zygote is too slow; the app zygote is required (worker lifecycle).** On the API 36 emulator the median time from `bindIsolatedService` to connected was 304 ms against a 300 ms budget; from the app zygote with the native library preloaded it was 45 ms. The same test showed that the app's `kill(2)` on its worker fails with `EPERM`, that YARA-X's in-process timeout fires on time under Pulley, and that unbinding ends a worker stuck mid-scan within milliseconds. Unbinding is therefore the controller's kill switch on Android (architecture §8.6).
12. **The X2 scenario script could pass a tamper test for the wrong reason (X2).** tuftool writes targets as links to the input files. Copied repositories shared those files, and on a device the links dangled, so "target modified → rejected" passed because the file was missing. The script now replaces links with copies after publishing, and every rejection must carry its expected reason (hash mismatch, signature threshold, size limit, and so on).

## Verified

- **L2:** with lockdown active, the worker cannot:
  - open a canary file, `/etc/passwd`, or list `/`;
  - create files;
  - open IPv4 or Unix sockets;
  - spawn processes;
  - ptrace or signal its parent;
  - map executable memory;
  - allocate beyond the 512 MiB address-space limit.

  Allowed work still succeeds: reading the passed fd with a matching checksum, a 64 MiB allocation, sealed output, and **YARA-X compiling a rule and matching a marker inside the locked-down worker**, so the Pulley interpreter needs no executable memory, no threads, and no file access beyond its input. In `ro-dir` mode, Landlock alone produces the denials (`EACCES`, distinct from seccomp's `EPERM`), which shows it is an independent layer. In `strict` mode a forbidden syscall kills the worker with SIGSYS.
- **L2 negative control:** every probe succeeds without lockdown, so the denials are caused by the lockdown and not by the environment. Without lockdown, the worker was able to `ptrace`-attach and freeze the controller (the first run deadlocked). That is concrete evidence of why the worker must never run unconfined.
- **L3:** after sealing (`WRITE|GROW|SHRINK|SEAL`), writes fail for both the worker and the controller. The controller verifies the seals before reading.
- **L1 (native WebKitGTK 2.54.1 in Docker):**
  - When `bwrap` cannot create namespaces, WebKit aborts instead of running unsandboxed.
  - When it can, the web process has NoNewPrivs=1, a seccomp filter, and new user, mount, pid and net namespaces, and the check allows browsing.
  - With the sandbox disabled through `WEBKIT_DISABLE_SANDBOX_THIS_IS_DANGEROUS=1` (negative control), the check refuses.
- **Android A1–A7 (API 30 with WebView 91, API 36 with WebView 133, emulators):**
  - The WebView renderer runs as `isolated_app` with no capabilities, NoNewPrivs=1 and a seccomp filter. From the page, `file://` and `content://` fetches, geolocation, clipboard reads, camera and microphone, `window.open` and `intent://` navigation all fail.
  - Six kinds of site state (cookie, server cookie, localStorage, IndexedDB, Cache Storage, service worker) are present within a session and absent after reset. When the controller is killed mid-reset, the state is still on disk; the next launch finds the marker, deletes it and moves to a new generation, and the probe again finds nothing.
  - URL downloads (GET, redirect, Content-Disposition, cookie-gated) are captured and re-fetched with matching hashes, and a hostile display name is normalized.
  - PdfRenderer renders identical pixels from a sealed memfd in the isolated worker. YARA-X compiles and matches there. The worker cannot read app files or storage, open inet sockets, resolve DNS, or use the clipboard.
  - Worker lifecycle: the app cannot signal its worker (`EPERM`); YARA-X's own 2 s timeout stops a runaway rule at 2001 ms; unbinding ends a worker stuck mid-scan within milliseconds and leaves no isolated process behind; workers from the app zygote start in 26–45 ms (median).
- **X1:** round trip across multiple STREAM chunks; truncation at four offsets and bit flips at four offsets are detected; a swapped object fails the hash check; a wrong key and a wrong passphrase are rejected; the size limit is enforced on the stream; `Debug` never prints the key. Index writes are atomic. A missing index recovers the previous one; a corrupt index fails instead of rolling back.
- **X2:** tough 0.24.0 with the filesystem transport rejects modified targets, unsigned metadata edits, a v1 replay after v2 was trusted, expired timestamps, an untrusted root, and timestamp metadata over 16 KiB, each for its expected reason. The arm64 Android build (tough with aws-lc-rs, cross-compiled with no changes) passes the same scenarios on the API 30 and API 36 emulators.
- **X3:** all 33 published Safe Browsing canonicalization examples pass, plus the three published expression examples. Per-URL decision latency against 1,000,000 entries on the host: p50 11.9 µs, p95 26.0 µs, p99 41.8 µs. Parsing and fully validating the 20 MB table takes 3.8 ms.

## Unverified (so far)

- L2/L3 on Fedora kernels, and inside Flatpak, where Flatpak's own seccomp filter also applies. (Ubuntu x86_64 passes in CI; there the ptrace negative control is inconclusive because Yama already blocks it.)
- X2 on x86_64 Android and physical phones; the size of tough and aws-lc-rs inside Rift's shared library (the standalone binary, 4.8 MB, is an upper bound).
- X3 latency on a real phone (the API 36 emulator gives p95 11.6 µs). Memory cost: ~19 MiB per million URL entries when held in a `Vec`.
- Android on physical devices, OEM WebView builds, API 33/34/35, x86_64, and 16 KB page-size devices. API 30 was run only with the image's stock WebView 91.
- L1 inside Flatpak (the shipping configuration), on a real desktop with a GPU, and with the Rust `webkit6` bindings instead of the Python probe. Whether the Flatpak sandbox bounds the network process.

## Could be improved

- The A1 harness picks the renderer as the newest `sandboxed_process`. It should diff the process list before and after the page loads.
- The Android worker should get a per-thread seccomp filter (finding 9) once it is shown not to break ART.
- Memory-map indicator tables instead of copying them, to reduce RSS for large packs. This needs one reviewed `unsafe` block or a vetted crate.
- The worker seccomp allowlist is hand-written per architecture. It should be generated, then confirmed by running the real parsers (YARA-X, PDFium, image decoders) under `strict` mode in CI.
- The vault index MAC key is derived from the identity's text encoding through HMAC. A dedicated HKDF context per purpose would be cleaner if more derived keys are added.
