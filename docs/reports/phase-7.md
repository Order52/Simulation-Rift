# Phase 7 report: hardening (Android, in progress)

**Status (20 Oct 2026):** started on Android. Phase 7 (§22) covers fuzz campaigns, fault injection, privacy captures, the ProxyController study and a dependency review, and its gate is §24's release gates. So far this report covers the privacy measurements (x1, x2), the dependency and licence review ([`dependencies.md`](dependencies.md)), the licence notices in both apps (l1), kill-fault injection (F1–F4), a full disk (F5/F6), power loss (P1–P4), the live page watch (w1, h1, h2), other apps on the same device (h3, H4), opening links (n5), page layout (r1), three hour-long fuzz campaigns over all ten targets, and the faults these found. Release-grade fuzzing and an external review have not started. "Verified" means tested on macOS arm64 and the API 35 emulator (16 KB pages, arm64, WebView 124), and in CI on API 33 and 34 (x86_64) where stated. Nothing here has run on a physical phone.

## Privacy (§17): what Rift sends by itself

§17 asks for traffic captures of (a) local scanning, (b) a manual update and (c) ordinary browsing. On an unrooted device Rift cannot capture packets, so the tests count **bytes per UID on real networks** from Android's own accounting (`dumpsys netstats`, after a forced poll, from its "UID stats" section). Two kinds of traffic are left out by that accounting, and the tests depend on it:

- **Loopback** belongs to no network and is not counted. The fixture server and the test's update server listen on 127.0.0.1.
- **The network lock's tunnel** (type 17, VPN) is left out on purpose: it is where the browser's packets go to be dropped, and nothing in it leaves the device.

A zero means nothing only if the measurement can see traffic. So x1 ends with a **control**: one TCP handshake from the controller's UID to 1.1.1.1:443, which must then be counted.

**What this does not show:**

- **Destinations.** Bytes are counted, not captured. x2 shows that the browser's UID moves nothing on real networks and that the controller's traffic grows. It does not show where the controller's bytes went; INV-13's destination checks are tested separately (S9, S25, `transfer` and `egress` tests).
- **Isolated workers' UIDs.** Preview and scan workers run under isolated UIDs (`u0_iN`), which x1 does not measure. They have no network access by construction (S4 checks that a socket fails), so they are expected to move nothing; that expectation is not measured here.
- **Longer idle periods.** 15 s of idling shows no polling at that scale; Doze-length periods were not measured.
- **The always-on VPN gap** (§24): if the controller dies, the lock goes with it. Not measured here.

### The ProxyController study (§10.3)

Architecture 2.1 replaced the study's question with a design: the browser app's WebView uses `ProxyController` with the implicit bypass rules removed, and the network lock (a VPN for the browser's UID only, which drops every packet) makes the proxy the only route out. x2 is the measurement: the browser's UID moved 0 bytes on real networks while its page loaded through the proxy. S26 (WebRTC and direct sockets have no route) and S28 (losing the lock ends the session) cover the other routes. The residual risk stays as §24 states it: escaped browser code can still reach loopback services.

## Dependency review

Recorded in [`dependencies.md`](dependencies.md): how dependencies are checked, what ships in each library, licences, and the security-sensitive dependencies with their versions, use and upstream. No RustSec advisory applies outside ten triaged exceptions: nine reached through `yara-x` (seven Wasmtime advisories, one Cranelift advisory, and `bincode`, which is unmaintained), and `basic-toml`, unmaintained and used only at build time. Each one's reason and exit condition is in `deny.toml`. Every licence is allowed, and all crates come from crates.io. The Android libraries are now locked like the crates (Gradle dependency locking: a `gradle.lockfile` per module, transitive versions included), and `android/scan-dependencies.sh` checks those on the runtime classpaths against OSV on every push. ## Live page watch (§10.5)

The browser's trusted bar now shows, while a page is open, what the session's pages have tried and a status: *Danger*, *Warning*, or *Nothing suspicious seen so far*, never "safe". Tapping it lists each event with how often and how long ago it was seen, and what is and is not watched; the home screen shows the same. Every event comes from a point where Rift enforces something: the core's navigation check, its egress proxy, the network lock, the download pipeline, and the engine's own permission callbacks. No script is injected into pages, so a page can neither see the watch nor write to it. Building it found that the threat database had never been used to check addresses (finding 9 below), and the proxy now checks every request's destination too.

## Other apps on the same device (§10.7)

Rift's isolation (separate apps and processes, the network lock, the wipe) is enforced by Android. But any other app the user installs can still reach Rift's windows through four features meant for helpers: overlays ("display over other apps"), autofill services, accessibility services and screen capture. These four are what Android banking malware uses. The tests install `outsider`, Rift's test app, as each kind of helper. They first show what it gets from one of its own windows, which is the control that proves each measurement can see something. Then they show what it gets from Rift's. Every check was also run against a build without the change (the baseline column), so each check is shown to fail when the defence is missing.

**What these do not cover.**
- An accessibility service that declares itself a tool (`isAccessibilityTool`) still reads everything. Google Play reviews that declaration, but sideloaded apps can make it freely.
- Below API 34 every accessibility service reads Rift's windows.
- Below API 31 overlays still show over Rift; only touches through them are dropped.
- The browser's window is not secure, so screenshots, screen recording and casting see pages (that is the user's own choice of what to capture). Since 2.3 neither is the controller's.
- The browser still tells the autofill service that a page field got the focus, so the service learns when the browser is in use and a field is focused.
- The input method (the keyboard) sees everything typed, by design; h2 only asks it not to learn.
- The attribution-reporting and enterprise sign-in settings of the WebView are set but not tested.
- None of this holds against an app with root, or against the system itself.

### Files from other apps

The owner also asked to view every file, not only downloads. Android now takes a file opened with Rift (`ACTION_VIEW` of a `content:` image, PDF or text) or shared to it (`ACTION_SEND` with `EXTRA_STREAM`, any type). The controller reads only the granted URI and streams it into the core's new `Intake` (rift-ffi `intake.rs`), which seals it into the session's quarantine exactly as a download: same reservation and 100 MiB limit, commit only when complete, cancelled at reset. It is then scanned and opened in a new full-screen viewer (pinch to zoom, double-tap to fit), which "View safely" on the home screen also opens. Two refusals: a URI whose provider is one of Rift's own packages (another app must not be able to make Rift read Rift's state), and `file:` paths, which reach the link check and are refused there by scheme. Each intake reads on its own thread, because the sending app controls how fast its content arrives and must not hold up downloads.

## Fault injection

The host kills the controller with `SIGKILL` (as the OS or a crash would) at a random moment while it writes, then starts it again and checks what is left. The test controller writes in a loop and logs each completed step, so the host knows how far it got before the kill. `RIFT_FAULT_ONLY=1` runs only these rounds; `RIFT_FAULT_ROUNDS` sets their number (8 by default).

| ID | Test | Result | Where |
|---|---|---|---|
| F1/F2, **removed in 2.3** with the vault | Kill while keeping files into the vault, then check the vault | **Pass (API 35, 8 of 8 kills, in four runs: alone, and in three full runs).** Kills came 0.05–3.0 s into each round, after 13–363 completed keeps. In CI on API 33 one round of eight failed: the vault was whole, but the kill had cut off an index write and its temporary file stayed (finding 12); unlock now removes it. Each time the vault opened, held every completed entry and at most one more (a keep whose kill came after its write but before its log line), had no stored file without an entry, and every entry exported to the exact bytes kept (SHA-256), with no plaintext marker anywhere in the app's files. | `f0`–`f2`, [evidence](evidence/phase7-faults-api35-16k/) |
| F3/F4 | Kill while installing the threat database, then check it | **Pass (8 of 8, in each of three runs).** One install takes about 0.5–1.2 s on this emulator, and kills came 0.01–1.2 s into it, plus one after it finished. Each time the database was either installed whole or still missing, never damaged; once installed it still found the demo file; and no update copy was left behind (after the fix in finding 6). | `f3`, `f4` |
| F5/F6 | A full disk: Rift's writes while `/data` is full, then what is left | **Pass (API 35: alone, in a full run and in a fault-only run, after the fixes; of two earlier solo runs, one found finding 14 and one failed on a race in the test itself).** The host, as root, fills `/data` up to what apps may use (the blocks ext4 reserves for the system stay free, so Android keeps working). | P3/P4 | Power cut while installing the threat database, then check it | **Pass (4 of 4).** The first cut came right after the install reported success, and the database was installed after the boot and still found the demo file. How the power cut works: the emulator's drives use qemu's `cache=unsafe`, which skips only the host's own fsync; every guest flush still hands qemu's caches (qcow2 metadata included) to the host, which keeps running. So what the guest had flushed survives and what it had not is lost, as on a power cut. Android itself needed one change: it writes its package list a few seconds after an install, so the first run lost the test packages to a cut; the script now reboots cleanly after its setup.

What this does not cover: real flash storage and its firmware (a phone's disk may reorder or drop writes it acknowledged, which an emulator cannot show), a disk that fills part-way through a write (F5 fills it first, so each write fails at its start), a kill of the browser app during a page load (S14 kills its renderer), an install that replaces one database with a different one under a power cut (P4 reinstalls the same demo database, so "old" and "new" look alike), and other Android versions. The power-loss rounds run locally (`android/power-loss.sh`), not in CI, since each round boots the emulator.

## Findings

1. **NAT64 addresses refused every IPv4-only host** (project status finding 50). The core refused all of `64:ff9b::/32` as non-public, and the proxy and the downloader refuse a name if any of its addresses is refused. On a DNS64 network (common on IPv6-only mobile networks) every IPv4-only host also resolves to `64:ff9b::<IPv4>`, so browsing and downloads to all of them were refused. The host network test found it: on this development network, `wrong.host.badssl.com` resolved to such an address. Fixed: an address in RFC 6052's well-known prefix `64:ff9b::/96` is judged by the IPv4 address it carries (so `64:ff9b::7f00:1`, loopback, and `64:ff9b::a9fe:a9fe`, link-local, are still refused). The rest of the /32, including RFC 8215's local-use `64:ff9b:1::/48`, stays refused, because the address it carries says nothing about where the translator sends it. `transfer` tests cover each case.
2. **Two crypto libraries shipped** (finding 51). `ureq`'s `rustls` feature brought `ring`, while `tough` uses `aws-lc-rs`. The core's TLS now uses rustls' aws-lc-rs provider, so `ring` is in no build. Size: arm64 7.76 → 7.50 MB and x86_64 8.66 → 8.99 MB for `librift_ffi.so` (aws-lc's x86_64 cipher code is now linked). Native code totals 19.2 MB (arm64) and 24.5 MB (x86_64), against the 25 MB budget (§18), so x86_64 has 0.5 MB left. TLS was rechecked on the host and on the device (x2).
3. **The scrypt work factor could refuse the right passphrase** (Phase 4 finding 6, project status 48). Found by a full run in this phase and fixed in Phase 4's code: every passphrase wrapping uses N = 2^17.
4. **The local emulator's DNS stopped answering** (finding 49). x1's control first used a host name and failed; the shell could not resolve names either. The control now uses an IP address, so a broken resolver cannot make the measurement look sensitive or insensitive by accident. A restart of the emulator fixed DNS.
5. **Twenty shipped crates publish no licence file** (finding 52). Found while generating the notices: they include YARA-X (BSD-3-Clause, whose notice must be reproduced), the uniffi crates (MPL-2.0) and several Wasmtime crates. Their texts now come from their repositories, pinned by version, and three crates have none anywhere (see [`dependencies.md`](dependencies.md)). JNA's archive also carries no licence text, although its native library contains libffi (MIT).
6. **A kill during an install left the update's copy behind** (finding 53). F4 found the working copy of the update under `files/rift/import` after a kill. It is Rift's own state, on the disposal allowlist, so it did not break isolation, but it stayed on disk until the next import. It is now removed at every start, on the update executor, so before any new install.
7. **An install asked for before the database was open did nothing, silently** (finding 54). F4's first version installed right after the start, while the database was still opening; nothing happened and the home screen said nothing. The first fix only said so, and w1 then hit the same race: its install was refused, so its session ran with no database. An install now waits (up to 30 s) for the database to be opened.
8. **A browser window that never attached came back on CI** (finding 47, open, finding 55). On API 34, Android removed a new browser window's task within milliseconds, right after a wipe, so the browser never registered. The cause is still not confirmed: Android 14's own data clear removes the app's recent tasks before it clears anything (AOSP `ActivityManagerService.clearApplicationUserData`), so it is not that; a receiver of the "package data cleared" broadcast, sent just before Rift is told the clear is done, is the remaining suspect. The home screen and the tests now use `Core.openWindow`, which opens the window again if the browser has not registered within 6 s (registration comes 0.2–1.3 s after the process starts), at most twice, and logs it. The same CI runs failed n4, which started its window directly; it now uses `Core.openWindow` too. l1 failed once on API 33 because the home screen had no scrollable view after 10 s; why is unknown, and the test now says what was in front.
9. **The threat database was never used to check addresses** (finding 56). The navigation check called the policy with no indicator table and "no database", so a listed address was never blocked as known malicious, while §10.3 said main-frame navigations were checked against it. Found while building the watch. The check now uses the installed database and its freshness, and the proxy checks every request's destination with it (subresources included), before resolving the name. w1 also showed that a listed `http://` image on a page from a secure origin is upgraded to HTTPS by the engine, so the proxy sees only its host; the demo database now has a host indicator (`listed.rift-demo.invalid`) besides its path indicator.
10. **The lock's own background traffic looked like an attempt** (found by w1). Android checks private DNS (TCP 853) and resolves (UDP 53) against the lock's resolver address on its own; the watch first reported this as "tried to connect directly". Traffic to that address on those ports, ICMP, IPv6 hop-by-hop and multicast are now treated as background: dropped as before, not reported.

11. **Pages laid out at zero height** (finding 58, found by H1). The browser's WebView had no layout parameters, so Compose's `AndroidView` gave it `WRAP_CONTENT`, and in that mode WebView lays pages out at zero height: `100vh`, `100dvh` and `100svh` were all 0 px while `innerHeight` was 714, so any page sized by viewport units collapsed (H1's striped page showed white). The WebView is now `MATCH_PARENT`; r1 checks it in the normal suite.
12. **A kill during an index write left its temporary file** (finding 59, found by F2 in CI on API 33). Unlock removed objects the index does not list but not `index.age.tmp`. It was ciphertext and never read, but the vault should hold only its own files; unlock now removes it, and the interrupted-save unit test covers it (it fails without the change).
13. **Tests that did not scroll on a small screen** (finding 60). CI's emulators have a 320x640 screen. w1 did not find the home screen's watch card, below the fold, and l1's tap on the licences button came while the column still moved from the last swipe, which only stops it. Both now scroll in bounded steps until the object is high enough and has stopped moving; w1, l1 and n3 passed twice at 320x640 on the API 35 emulator. The product was not at fault. On CI's API 34 (b3beb0c) w1 still did not reach the card in 30 quick swipes down, most likely because a fling carried it past; the search now swipes slowly, goes back up if the way down misses, and on failure lists what was on screen. w1, l1 and n3 passed twice more at 320x640 on API 35, where the way back up was not needed, so CI's API 34 is the check of that part.
14. **A full disk was reported as a build without the demo database** (finding 62). F5's first run: the install on a full disk said "the demo database is not available in this build: … ENOENT". Copying the database failed because `mkdirs` cannot create a directory on a full disk, and reports that only by returning false, which the copy did not check; the next open then failed with "no such file". The install now checks the build's assets first, checks each directory it creates, says "the demo database could not be copied, so nothing was installed: …", and removes what it had copied. The installed database was never at risk.
15. **Some invisible and reordering characters reached Rift's own UI unescaped** (finding 63). Text from websites and files (file names, file text shown as plain text, host names in warnings and in the live watch) is shown with control characters and a list of bidi and zero-width characters escaped. Writing the property for the new `trusted_text` fuzz target against Unicode's own Bidi_Control list showed that the list missed U+061C (ARABIC LETTER MARK, a bidi control), and with it other format characters: the word joiner, invisible operators, the deprecated shaping controls and the tag characters U+E0020–E007F, which are used to hide text. A unit test confirmed it on the old code. Rift now escapes Unicode's whole format category (Cf, 16.0, compared with Python's `unicodedata`: the same 21 ranges). It was found by reading, not by the fuzzer: two minutes of `trusted_text` (0.8 M runs) did not reach these code points.
16. **A padded address passed the proxy's database check** (finding 65, found by the first long fuzz campaign). `url_canonicalize` showed that canonicalization was not a fixed point: it bounded only its input, and escaping can triple a URL's length, so a canonical form could be too long to canonicalize again. Following that into the proxy: a plain-HTTP request for a listed path, padded past what canonicalization takes (8 KiB) but inside the proxy's 16 KiB head limit, was screened by its host alone and forwarded (a test got 200 OK). The proxy now refuses an address it cannot check ("not checked"), the live watch shows it as a warning, and a canonical form over the limit is refused too (9354fad).
17. **The vault screens were never secure** (finding 68, found by h3). INV-12 says vault screens set `FLAG_SECURE`, but no code set it: a screenshot taken with the vault unlocked showed it (0.0 % black). The controller's window is now secure while the vault is unlocked (99.8 % black) and not otherwise, so the rest of the home screen can still be captured.
18. **"No autofill" was not enforced** (finding 69, found by h3). §10.1 says Rift has no autofill, but nothing kept the system's autofill service out. A third-party autofill service got fill requests when the home screen's address field was tapped and when a field of a page's sign-in form was tapped (the baseline run logged where each request came from, not what was in it). Excluding the window's views was not enough. Compose's text fields and WebView each report to autofill themselves: Compose's root view always says it is important for autofill, and WebView sends its page as virtual views. Compose fields are now marked as holding no autofill data. The WebView describes no page, accepts no fill and saves no form data. The engine still sends one request when a page field is focused, but the request holds nothing.
19. **Other apps could draw over Rift and read its screen** (finding 70, found by h3 and H4). An app with "display over other apps" covered 97 % of both apps' windows, so it could have relabelled the trusted bar or a warning. A non-tool accessibility service read the home screen's texts. Both apps now hide other apps' overlays (API 31+), or drop touches through them on API 30. Both also mark their windows' content as for accessibility tools only (API 34+). Neither change helps against an accessibility service that declares itself a tool.

20. **The checks and the engine read some addresses differently** (finding 71, found by the links audit). The navigation check judged an address with the Safe Browsing canonicalization, which is deliberately loose, while WebView parses it with the WHATWG URL standard. For links Rift loads itself (from other apps, shared, typed), the two disagreed. `https://evil.example\@good.example/` was looked up in the database, and checked for lookalikes, as `good.example`, while WebView opened `evil.example`. A host with spaces ("https://Check this out: https://…", what a shared message became) passed the check, and WebView then loaded nothing, with no message. The proxy's own check of every connection's host still applied, so a listed host was refused at connection time. The interstitial and the lookalike warning could be bypassed, though. The core now parses every address as the engine does and checks that form. `typed_address` returns it, so the browser loads exactly what was judged, and an address the engine could not load is refused as invalid.
21. **An engine that had not drawn a page covered the trusted bar** (finding 72, found by n5). A WebView that had shown no page yet (for example, when a session's first link was blocked) filled its whole clip with its background. Compose does not clip an embedded view to its bounds, so this covered Rift's bar and the system bars in black until a page loaded. The bar's controls were still there for accessibility, but not visible. The engine's area is now clipped, and the bar is drawn above it. n5 measures the bar: 100 % black before the fix, 0 % after.
22. **Links from other apps were dropped or shared a session** (finding 73, found by the links audit). A link shared inside a message (as most apps share links) was silently ignored (finding 20). Every link from another app also opened in the current session, beside whatever pages were already open. Shared text now gives its first link, defanged spellings included. A link from another app opens in a new, wiped session whenever the current one has loaded a page.
23. **A launch after a kill could fail its cleanup** (finding 74, found by F4 in CI). Android was still stopping the browser app for the killed launch's wipe when the next launch bound to it, so the binding died and the reset failed closed. The bind to the instance to be wiped and its first calls are now retried, as the bind to the fresh instance already was. Forced stops during start: 13 of 20 starts failed before, 1 of 20 after; F4 then passed 20 of 20 rounds on the API 34 emulator.
24. **A stop could hit the wipe request itself** (finding 75, found while reproducing finding 74). The controller could not tell whether a browser that died during the wipe call had asked Android first. The browser now answers before asking, so a failed call means it never asked, and the controller asks again (twice at most). Forced stops during start: 50 of 50 started a session; kills: 40 of 40 (API 34 emulator).
25. **The outsider's window sometimes did not show** (finding 76, found by h3). A second launch reached the previous, closing window. Each command now starts it in a fresh task.
26. **Extra isolation could leave the browser's clipboard blocked** (findings 81 and 83, found by z1). Undoing with `default` stored a mode the clipboard service also refuses, and clearing Rift's data with the switch on lost the record that anything was changed. The helper now restores `allow`, and Rift undoes leftovers whenever a Shizuku that allowed it is running.
27. **The helper outlived Rift** (finding 84). Shizuku's end-the-helper call carries no interface token and was refused; the helper now answers it.
28. **The network lock started before there was a browser to lock** (finding 85). Found while building the one-file install: the VPN applied to no app. It now starts after the install.
29. **Switching the lock off left the VPN up** (finding 86, found by s28c). Android stays bound to the VPN service while its tun is open; the service now closes the tun itself.
30. **z1 probed the previous session's firewall rules** (finding 87). A race in the test; it now waits for the rules written for the new port.
